## 改动 1：关掉虚拟导航栏（3 处属性）

这是**唯一会影响你看到的东西**的改动。

### 为什么要改

RestlessOS 是 phh 系 treble GSI。「treble GSI」的意思是一套系统要给**几百种不同手机**
用，所以作者得猜一个默认值。phh 的猜法是：

> 假设这台设备**没有实体按键**，所以永远画一排虚拟导航栏。

但小米 6 **有实体键**：

| 物理位置 | 功能 | Linux keycode |
|---|---|---|
| 屏幕下方左侧 | 返回 | `158` (BACK) |
| 屏幕下方右侧 | 多任务 | `139` (APP_SWITCH) |
| 正面指纹键 | 回桌面 | `102` (HOME) |

所以原版刷上去会变成：**屏幕底下多一条白条/手势条，但底下的实体键也能用** —— 又丑又挤，
而且那条虚拟栏还占掉 48dp 的屏幕高度。

> 我的参照系是 AviumUI（另一个国产 LOS 定制）。它跑在同样的 LOS 22.2 底层上，
> 它的 `build.prop` 里**根本没有这几个属性**，所以它默认就是干净的。
> 这说明了正确做法：不要这些属性，而不是设成某个值。

### 改了三处

#### ① `/system/build.prop`

```diff
- persist.sys.phh.mainkeys=0
+ persist.sys.phh.mainkeys=1
```

**`mainkeys` 是什么**：phh 的 `rw-system.sh` 启动脚本里，这行是「设备有没有实体键」的开关。

- `0` = 没有实体键 → 系统画虚拟导航栏
- `1` = 有实体键 → 系统不画

原值 `0` 是 phh 给绝大多数"全面屏无实体键"设备的默认值。

> 顺带说：phh 的脚本里唯一一处 `setprop persist.sys.phh.mainkeys 0` 是给
> Realme RMX1941/1942/1943/1945 这几台机器特判的（见 `rw-system.sh` 第 1101 行），
> 说明这个属性的语义确实是「强制开关导航栏」。

#### ② `/system/build.prop`（新增一行）

```diff
+ # MI 6 有实体键（返回/多任务 + 指纹 Home），不要虚拟导航栏
+ qemu.hw.mainkeys=1
```

**`qemu.hw.mainkeys` 是什么**：这是 **AOSP 原生**的标准属性（不是 phh 私货）。
Android 框架的 `PhoneWindowManager` 读它来决定要不要画导航栏，语义是：

- `1` = 有硬件键，`config_showNavigationBar` 强制为 false
- `0` = 没硬件键

加这条是双保险 —— 万一 phh 的 `mainkeys` 被别的逻辑覆盖了，AOSP 这层还拦着。

> 为什么加在文件末尾而不是插在中间？因为 `build.prop` 是逐行解析的，
> 位置无所谓，但末尾更好找。我在前面加了注释说明原因。

#### ③ `/system/product/etc/build.prop`

```diff
- ro.boot.vendor.overlay.theme=com.android.internal.systemui.navbar.gestural
+ ro.boot.vendor.overlay.theme=
```

**这行是什么**：它指定开机时强制启用哪个 RRO overlay（运行时资源替换）。
`navbar.gestural` 就是"手势导航"那个 overlay，它会把 `config_showNavigationBar` 覆盖成 true。

**为什么留空而不是删掉整行**：

- 删掉整行也能工作，但有些代码会 `getprop` 然后判空，留空字符串和"不存在"在某些
  实现里行为不同（`getprop` 对不存在的 key 返回空字符串，所以其实一样）；
- 留空更保守 —— 只清值，不改行数，diff 更好看。

> 注意：这行在 `product/etc/build.prop` 而不是 `system/build.prop`。
> Android 10 之后 build.prop 被拆成 system / product / system_ext / vendor 四份，
> 找属性得四个文件都看。

### 我**没有**删 overlays

原版 `system/product/overlay/` 里有：

- `NavigationBarModeGestural/NavigationBarModeGesturalOverlay.apk`
- `NavigationBarMode3Button/NavigationBarMode3ButtonOverlay.apk`
- `NavigationBarMode2Button/`
- `treble-overlay-NavBar.apk`
- `TransparentNavigationBar/`

**这些我全都留着了。**

**为什么不删**：删 APK 会让 RRO 索引表残缺。Android 启动时会扫描 `/product/overlay/`，
如果某个 overlay 的 .apk 不见了但还在 `overlay.list` 或资源缓存里，可能导致
`OverlayManagerService` 报错甚至启动失败。改属性已经足够，没必要冒这个风险。

**副作用**：你还能在 设置 → 系统 → 手势 → 系统导航方式 里手动切回手势/三键。
如果我想彻底锁死成实体键模式，就得删这些 APK —— 但那样你就没法改回去了，不划算。

### 验证方法

```bash
# 挂载或解出 system.img 之后
debugfs -R "cat /system/build.prop" system.img | grep mainkeys
# 期望看到两行：
#   persist.sys.phh.mainkeys=1
#   qemu.hw.mainkeys=1

debugfs -R "cat /system/product/etc/build.prop" system.img | grep overlay.theme
# 期望：ro.boot.vendor.overlay.theme=   （等号后面是空的）

# 确认 overlay 都还在
debugfs -R "ls /system/product/overlay" system.img | tr ' ' '\n' | grep -c Navigation
# 期望：3（Gestural / 3Button / 2Button 三个目录）
```

## 改动 2：system 镜像补零到 5 GiB

### 改了什么

| | 大小 | 块数 |
|---|---|---|
| 原始 GSI 镜像 | 3 156 676 608 B | 770 673 |
| 刷进去的 | 5 368 709 120 B | 1 310 720 |

后面 540 047 块（约 2.06 GiB）全是零。

### 为什么要补

小米 6 的 `system` 分区实际是 **5 GiB**（`fastboot getvar partition-size:system`
返回 `0x140000000`）。

`fastboot flash` 只会写你给它的那么多字节，**剩下的是上次系统留下的旧数据**。

这本身不致命（ext4 超级块里写着有效的块数，多出来的部分不算数），但有两个坏处：

1. 如果你第一次刷的是 AviumUI（5.3 GB），再刷这个 3.1 GB 的 GSI，分区尾巴上会留着
   AviumUI 的残块。某些情况下（比如 fsck、OTA）可能读到脏数据。
2. 心理上不干净。

补零之后整块分区内容确定，没有历史残留。

### 怎么补的

```bash
cp --reflink=auto system.img system-padded.img
truncate -s 5368709120 system-padded.img
```

`truncate` 扩展出来的部分是 hole（稀疏文件），不占实际磁盘，读出来是零。
`fastboot` 发的时候就自动按 sparse 跳过这些零块，所以**不影响刷机速度**。

> 所以你看到的 `Sending sparse 'system' 1/6 (524236 KB)` 只有 6 块，
> 而不是 10 块 —— 因为后半段全是零，fastboot 跳过了。

## 改动 3：重新打包成 block-OTA

### 改了什么

把 raw 的 `system.img` 转成 Android OTA 用的格式：

- `system.transfer.list` —— 告诉 recovery 每个块写到哪个位置
- `system.new.dat.br` —— 实际数据，brotli 压缩

### 为什么

原版 GSI 是 raw img，只能 `fastboot flash system`。想做成 sideload 能刷的 zip，
必须转成 block-OTA 格式（这是 Android 从 5.0 开始的标准 OTA 格式）。

### 具体参数

生成时**没有写全局 `erase` 命令**。

LOS 官方的 transfer.list 第一行是：

```
erase 6,108595,163328,164354,196096,197121,212992
```

意思是「先把这些块区抹零」。但紧接着的 `new`/`zero` 命令已经全量覆盖了每一个块，
这个 erase 纯粹是浪费 —— 在 5 GiB 分区上会多花好几分钟，还可能超时（我实测过
AviumUI 那套就因为 erase 太慢导致 updater 崩）。

所以我的 transfer.list 只有：

```
4
1310720
0
0
new  2,0,720904
zero 2,720904,720912
new  2,720912,750260
...
zero 2,770673,1310720
```

第一行 `4` = 格式版本；第二行 `1310720` = 总块数（5 GiB ÷ 4096）；
后面每行 `<op> <N>,<start>,<end>` = 操作 + 块区间。

### brotli 用 quality 6 不用 9

| quality | 速度 | 3.1 GB 耗时 | 产出大小 |
|---|---|---|---|
| 9 | 1.2 MB/s | **2600 秒** | 约 1.10 GB |
| 6 | 11.6 MB/s | **256 秒** | 1.18 GB |

q6 的包大 7%，但快 10 倍。对分发来说这个取舍明显划算。

### 验证

我做了逐字节比对：把 `transfer.list` + `new.dat.br` 还原回 raw 镜像，
跟原始 `system.img` 一个字节一个字节比：

```
total_blocks=770673 (3156676608 bytes)
consumed=3122270208  dat_size=1177350712
多余解压字节=0（应为 0）
✅ 逐字节比对通过
```

`consumed` 比 `total` 少，是因为中间有 `zero` 段（那些块不占 dat 里的字节）。

## 改动 4：vendor 换成 LineageOS 22.2 的

### 改了什么

原版 RestlessOS 只有 `system.img`，**没有 vendor**。我用的是 LineageOS 22.2
（2026-10-09 nightly）里那份 `vendor.new.dat.br`，原样搬过来。

### 为什么必须换

小米 6 出厂时 vendor 是 **Android 9** 的（MIUI 11 时代）。

RestlessOS 是 **Android 16**。A16 的 system 要求 vendor 提供的东西（HAL 接口、
VNDK 版本、SELinux 策略）比 A9 新太多。直接拿 A9 的 vendor 配 A16 的 system，
大概率开不了机。

**LineageOS 22.2 用 Android 15 重建了 vendor**，这是整套方案能跑的关键前提。
A15 的 vendor 配 A16 的 system 是可行的（差一个大版本，VNDK 有向后兼容）。

> 这需要先刷一次 LOS 22.2 吗？**不需要。** 我把 LOS 的 vendor 一起打进了包，
> 所以从原厂 MIUI 直接刷这套包，vendor 会一起被换掉。

### 写到哪个分区

**`cust`，不是 `vendor`。**

小米 6 的分区表里没有 `vendor` 分区，`/vendor` 实际是从 `cust` 挂载的。
这是小米从 MIUI 时代留下来的设计（见 LOS 的 `fstab.qcom`）：

```
/dev/block/bootdevice/by-name/cust    /vendor    ext4  wait,first_stage_mount
```

所以 `fastboot flash cust vendor.img`，写错了刷不进或者刷到没用的地方。

### 没改 vendor 的内容

`vendor.new.dat.br` 和 `vendor.transfer.list` 是**原封不动**从 LOS 官方 zip 里搬的，
一个字节没动。我只做了：
1. 解压 → 得到 raw `vendor.img`（给方式 B 直接刷用）
2. 原样的 `.new.dat.br` 打进 zip（给方式 A 用）

### 验证

```
total_blocks=110646
vendor payload roundtrip OK
```

（还原回来跟 LOS 的 vendor.img 逐字节一致）

## 改动 5：updater-script 重写

### 改了什么

zip 里 `META-INF/com/google/android/updater-script` 是我重写的。

原版 LOS 的：

```
assert(getprop("ro.product.device") == "sagit" || ...);
assert(xiaomi.verify_trustzone("TZ.BF.4.0.6-00178") == "1" || ...);
ui_print("Target: Xiaomi/sagit/sagit:8.0.0/...");
package_extract_dir("install", "/tmp/install");
set_metadata_recursive(...);
run_program("/tmp/install/bin/backuptool.sh", "backup", ...);
ui_print("Patching system image unconditionally...");
block_image_update("...system", "system.transfer.list", "system.new.dat.br", ...);
block_image_update("...cust", "vendor.transfer.list", "vendor.new.dat.br", ...);
run_program("/tmp/install/bin/backuptool.sh", "restore", ...);
package_extract_file("boot.img", "...boot");
```

我的：

```
assert(getprop("ro.product.device") == "sagit" || ...);        # 保留
assert(xiaomi.verify_trustzone("TZ.BF.4.0.6-00178") == "1");  # 保留
ui_print("=========================================");         # 新加
ui_print("  RestlessOS 16.0.0  for Xiaomi MI 6");             # 新加
ui_print("  system : RestlessOS GSI (Android 16)");           # 新加
ui_print("  vendor : LineageOS 22.2 (Android 15)");           # 新加
ui_print("=========================================");
block_image_update("...system", ...);                          # 保留
block_image_update("...cust", ...);                            # 保留
package_extract_file("boot.img", "...boot");                  # 保留
```

### 具体差异

| 改动 | 原因 |
|---|---|
| **删掉** `backuptool.sh` 的 backup/restore | 那是 LOS 的"OTA 时保留 Magisk 和 GApps"机制。这个包不是 OTA，用户会清数据，跑了也没用，还可能出错 |
| **删掉** `package_extract_dir("install", ...)` | 同上，backuptool 相关 |
| **删掉** `set_metadata_recursive` | 同上 |
| **删掉** 写 `recovery.img` | 就为了留一条退路。如果 recovery 也换了，刷坏了就没东西救 |
| **改** 进度条权重 | system 占绝大部分时间，给 0.85；vendor 0.10；boot 0.05 |
| **加** 几条 `ui_print` | 让人知道自己在刷什么 |

### 保留的两个 assert

```
assert(getprop("ro.product.device") == "sagit" || ...);
assert(xiaomi.verify_trustzone("TZ.BF.4.0.6-00178") == "1" || ...);
```

第一条拦住刷错机型。第二条要求 MIUI 固件 ≥ 9.5.16（trustzone 版本检查）。

> **第二条是 LOS 的遗留要求**，理论上原厂更老的 MIUI 也可能过不去。
> 但实测：手机上 vendor 从 A9 换到 A15 之后，这条检查是通过的
> （因为 trustzone 读的是 /firmware 分区，不是 vendor）。
> 如果你的机器刷不过去，说明固件太老，先用 MiFlash 刷一次较新的 MIUI 再回来。

## 怎么自己验证

如果你不信任我这个描述（应该的），全部可以自己查。

### 1. 看属性

```bash
# 需要 system.img
debugfs -R "cat /system/build.prop" system.img > /tmp/a.txt
grep -nE 'mainkeys|qemu.hw' /tmp/a.txt

debugfs -R "cat /system/product/etc/build.prop" system.img > /tmp/b.txt
grep -n 'overlay.theme' /tmp/b.txt
```

### 2. 文件系统完整性

```bash
e2fsck -fn system.img
```

应该输出：

```
/: 5013/5376 文件（3.9% 不连续），750276/758491 块
```

**5013 个文件** —— 跟原始镜像一样。如果我删过东西，这个数字会变大或变小。

### 3. 逐字节还原比对

```bash
./scripts/verify_payload.py \
    payload/system.transfer.list \
    payload/system.new.dat.br \
    system.img
```

应该输出 `✅ 逐字节比对通过`。

### 4. 对着原始镜像比 diff

这是最彻底的：

```bash
# 下载原始 GSI
./scripts/fetch-gsi.sh
# 自己打一份补丁
cp --reflink=auto RestlessOS-arm64-ab-16.0.0-202606230923.img mine.img
./scripts/patch-navbar.py mine.img --dry-run   # 先看要改什么
```

`--dry-run` 会把要改的每一行打出来，**不写盘**。你可以拿它对着本文档核。

### 5. 看 zip 里到底有什么

```bash
unzip -l sagit-RestlessOS-*.zip
```

15 个文件，跟 LineageOS 官方 zip 的清单一一对应。
